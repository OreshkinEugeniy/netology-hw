# Домашнее задание к занятию "`Репликация и масштабирование. Часть 2`" - `Орешкин Евгений`


### Задание 1

Опишите основные преимущества использования масштабирования методами:

активный master-сервер и пассивный репликационный slave-сервер;
master-сервер и несколько slave-серверов;
Дайте ответ в свободной форме.

Активный master-сервер и пассивный slave-сервер

При такой архитектуре все операции чтения и изменения данных выполняются на активном master-сервере. Slave-сервер получает копию данных с master-сервера, но в обычном режиме не обслуживает запросы приложения.

Основные преимущества:

повышение отказоустойчивости базы данных;
наличие актуальной резервной копии на отдельном сервере;
возможность переключить приложение на slave-сервер при отказе master-сервера;
проведение обслуживания или обновления master-сервера с меньшим временем простоя;
резервное копирование можно выполнять со slave-сервера, не создавая дополнительную нагрузку на master;
архитектура относительно проста в настройке и сопровождении.

Если master-сервер выходит из строя, slave переводится в режим нового master-сервера. Переключение может выполняться вручную либо автоматически при помощи системы управления кластером.

При асинхронной репликации между master и slave может возникать небольшая задержка. Поэтому при аварийном переключении существует риск потери последних транзакций, которые ещё не успели передаться на slave.

Master-сервер и несколько slave-серверов

В этой архитектуре операции записи выполняются на одном master-сервере, а операции чтения могут распределяться между несколькими slave-серверами.

Основные преимущества:

горизонтальное масштабирование операций чтения;
распределение запросов между несколькими серверами;
уменьшение нагрузки на master-сервер;
повышение производительности при большом количестве пользователей;
отчёты и аналитические запросы можно направлять на отдельный slave;
резервное копирование можно выполнять со slave-сервера;
при отказе master один из slave-серверов может быть назначен новым master;
наличие нескольких копий данных повышает отказоустойчивость системы;
новые slave-серверы можно добавлять по мере увеличения нагрузки.

Например, запросы INSERT, UPDATE и DELETE направляются на master, а запросы SELECT распределяются между slave-серверами балансировщиком.

Недостатком остаётся то, что master является единственной точкой записи. Увеличение количества slave-серверов масштабирует в первую очередь чтение, но не запись. Кроме того, из-за задержки репликации данные на slave некоторое время могут отличаться от данных на master.

### Задание 2
Разработайте план для выполнения горизонтального и вертикального шаринга базы данных. База данных состоит из трёх таблиц:

пользователи,
книги,
магазины (столбцы произвольно).
Опишите принципы построения системы и их разграничение или разбивку между базами данных.

Пришлите блоксхему, где и что будет располагаться. Опишите, в каких режимах будут работать сервера.

Для примера база данных интернет-магазина книг будет состоять из следующих таблиц:

users (
    user_id,
    login,
    password_hash,
    full_name,
    email,
    region_id,
    created_at
)

books (
    book_id,
    category_id,
    title,
    author,
    description,
    price,
    stock_count
)

stores (
    store_id,
    region_id,
    name,
    address,
    phone,
    working_hours
)

При построении системы будут использоваться два вида шардинга:

вертикальный шардинг — разделение данных по столбцам или функциональному назначению;
горизонтальный шардинг — разделение строк таблиц между несколькими серверами.
Вертикальный шардинг

Сначала разделим часто используемые и дополнительные данные.

База данных пользователей

На первом сервере располагаются основные данные, необходимые для авторизации:

users_auth (
    user_id,
    login,
    password_hash
)

На втором сервере располагаются персональные данные пользователей:

users_profile (
    user_id,
    full_name,
    email,
    region_id,
    created_at
)

Такое разделение позволяет отдельно защитить данные авторизации и независимо масштабировать сервис профилей пользователей.

База данных книг

Основные сведения о книге размещаются отдельно:

books_catalog (
    book_id,
    category_id,
    title,
    author,
    price
)

Большие и реже используемые данные размещаются на другом сервере:

books_details (
    book_id,
    description,
    stock_count
)

Благодаря этому обычный просмотр каталога не требует загрузки больших описаний книг.

База данных магазинов

Основные данные магазина:

stores_main (
    store_id,
    region_id,
    name
)

Контактная информация:

stores_contacts (
    store_id,
    address,
    phone,
    working_hours
)

Горизонтальный шардинг

После вертикального разделения таблицы можно дополнительно разбить по строкам.

Пользователи

Пользователей лучше распределять по хешу идентификатора:

Шард 1: user_id % 2 = 0
Шард 2: user_id % 2 = 1

Хеширование обеспечивает приблизительно равномерное распределение пользователей между серверами.

Обе части пользовательских данных должны использовать одно правило. Например, данные пользователя с user_id = 10 должны находиться на первом шарде и в users_auth, и в users_profile.

Книги

По аналогии с примером из презентации книги можно разделить по категориям:

Шард 1: category_id <= 3
Шард 2: category_id > 3 AND category_id <= 6
Шард 3: category_id > 6

Таким образом, каждый сервер будет хранить книги только определённых категорий.

Для предотвращения ошибочной записи на каждом шарде можно добавить ограничение CHECK:

CHECK (category_id <= 3)

или соответствующее условие для другого диапазона.

Магазины

Магазины удобно распределить по регионам:

Шард 1: Москва
Шард 2: Московская область
Шард 3: остальные регионы

Такое разделение удобно, поскольку большинство запросов на поиск магазинов выполняется внутри определённого региона.

Режимы работы серверов

Каждый шард работает как самостоятельный сервер базы данных:

основной сервер шарда работает в режиме master;
все операции чтения и записи своего диапазона данных выполняются на master;
для каждого master создаётся пассивный slave;
slave получает изменения посредством репликации;
при отказе master его slave переводится в активный режим;
маршрутизатор направляет запрос на нужный шард в зависимости от идентификатора, категории или региона.

Принципы построения системы
Приложение не должно самостоятельно перебирать все серверы. Выбор нужного шарда выполняет маршрутизатор запросов.
Правила распределения должны быть однозначными. По значению user_id, category_id или region_id должно быть возможно определить один конкретный шард.
Идентификаторы объектов должны быть уникальными во всей системе. Для этого можно использовать UUID либо отдельный сервис генерации идентификаторов.
Между разными шардами не следует создавать обычные внешние ключи. Целостность таких связей должна контролироваться приложением.
Запросы к одному шарду выполняются быстрее, поскольку сервер обрабатывает только часть общего объёма данных.
Запросы, затрагивающие все шарды, например подсчёт общего количества книг, выполняются на каждом сервере, после чего маршрутизатор объединяет результаты.
Для каждого master-сервера необходим отдельный slave, чтобы отказ одного физического сервера не приводил к потере соответствующего сегмента базы данных.

В результате вертикальный шардинг уменьшает количество столбцов и разделяет данные по назначению, а горизонтальный шардинг уменьшает количество строк на каждом сервере. Их совместное применение позволяет независимо масштабировать пользователей, каталог книг и магазины.
